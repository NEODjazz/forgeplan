# Ресурсы и назначения 0.4

## Модель

Resource: стабильный ResourceId, name, kind person/generic, base capacity,
availability periods. IDs ресурсов и задач — разные Rust-типы, у обоих свой
allocator. Материальные/стоимостные ресурсы и ставки ещё не реализованы.

Units — целые basis points: 10000 = 100%, 2550 = 25,5%, максимум 1000000 =
10000%. Capacity может быть нулевой; units назначения должны быть >0.
Assignment — уникальная пара (TaskId, ResourceId) с постоянными units на всём
рабочем span задачи. Summary assignments запрещены; веха даёт работу/нагрузку 0.

Availability — from/through включительно в локальных датах проекта + capacity.
Период заменяет base capacity; вне периодов используется base. Пересечения
и обратные даты запрещены. Периоды в нерабочие дни не создают рабочие часы.
Индивидуальных недельных/часовых календарей пока нет: рабочие интервалы общие.
Будущий отпуск не расширяет горизонт и не вызывает бесконечный календарный скан.

## Единицы работы

Работа назначения: duration_minutes * units_bp / 10000. Внутри ядра хранится
целое minute*basis_points, т.е. 1/10000 рабочей минуты. Пример: 1 минута при
33,33% = 0,3333 минуты. В процессе расчёта округления нет. JSON отдаёт десятичные
минуты; UI часы округляет для отображения. Длительность задачи при изменении
units не меняется. Это fixed-duration uniform demand, не effort-driven engine.

Работа задачи — сумма назначений; работа summary — сумма потомков (включая
вложенные summary один раз), независимо от span. Загрузка — плановая потребность,
а не обещание выполнимости: при отсутствии человека demand остаётся и образует
перегрузку. Факт/remaining work/overtime/booking types не моделируются.

## Sweep расчёт

Для каждого ресурса строятся события начала/окончания назначений и изменения
capacity в общих рабочих координатах. Интервалы полуоткрытые [ES,EF): конец
одной задачи и начало другой в одной координате не создают ложной перегрузки.
На каждом сегменте demand — сумма units активных задач; excess=max(demand-cap,0).

planned work = интеграл demand; capacity work = интеграл capacity;
excess work = интеграл excess; overloaded_minutes — рабочее время с excess>0.
Нельзя заменять excess на max(дневная работа - дневная capacity,0): одновременная
перегрузка может существовать при низкой средней занятости. Отчёт хранит оба
типа данных, peak units и список активных задач на перегруженном сегменте.

Диапазоны overloads представлены по рабочему времени. Между start/finish
могут быть выходные/перерывы; они не включаются в working_minutes. Список
делится по событиям назначений/capacity, не по каждой календарной паузе.
Daily строки интегрируют сегменты по рабочим датам; выходные без работы не выводятся.
Capacity считается только в рабочем горизонте проекта, последний неполный день
обрезается по его окончанию. Это не месячный HR capacity report за полный месяц.

## Отображение и ограничения

Полные итоги вычисляются для всего проекта. Daily — первые 90 рабочих дат,
с daily_truncated. Overloads — первые 200 сегментов/ресурс с overloads_truncated
и полным overload_count. В каждом сегменте выводятся первые 20 task_ids и полный
active_task_count. Лимиты не уменьшают totals. UI сообщает о сокращении таблицы.
Постраничный диапазон дат/экспорт полного time-phased отчёта — будущая задача.

Не более 200 ресурсов, 10000 назначений, 5000 availability periods на проект.
Данные валидируются при parse/apply до commit. Удаление ресурса удаляет его
назначения; DeleteSubtree очищает назначения потомков. Undo/Redo восстанавливает
снимок целиком. Ошибки unknown ID/duplicate/summary/overlap оставляют всё неизменным.

## Что не делается автоматически

Назначения, capacity и отпуск не сдвигают задачи и не меняют CPM. Ресурсное
выравнивание с preview/rollback будет явной отдельной операцией. Не реализованы
resource calendars, профили/контуры, несколько ресурсов с разной скоростью,
fixed-work/fixed-units, multi-project pool, персональные часовые пояса и стоимость.
